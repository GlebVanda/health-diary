# Принятые решения

Где ТЗ допускает несколько вариантов или локальная версия расходится с ТЗ, выбран самый простой вариант. Здесь — что и почему.

## Отличия локальной версии от ТЗ

| ТЗ | Локальная версия | Почему |
|---|---|---|
| Next.js + Supabase + Vercel | Статическое HTML + JS, данные в IndexedDB | Решение заказчика: первая версия без Git, облака и установки Node.js |
| PIN проверяется на сервере, хэш в `APP_PIN_HASH` (bcrypt) | PIN задаётся при первом запуске, SHA-256 с солью в локальном хранилище | Сервера нет. PIN защищает от случайного доступа к экрану, но не от того, у кого есть доступ к файлам браузера |
| httpOnly-cookie на 90 дней | Метка сессии в `localStorage` на 90 дней | То же |
| Ограничение перебора по IP | Счётчик попыток на устройстве | IP нет |
| Переменные `AI_PROVIDER`, `AI_API_KEY`, `AI_MODEL` | Те же поля в Настройках, хранятся в браузере | Нет окружения сервера; `.env.example` появится вместе с Next.js |
| `scripts/import-xlsx.ts` с `--dry-run` | Экран «Импорт из Excel»: пробный прогон с отчётом → кнопка «Импортировать» | Без Node скрипт не запустить; логика та же (поиск недель по датам, upsert, проверки) |
| Recharts, shadcn/ui, Tailwind | Свои SVG-графики и CSS | Без сборки и без внешних зависимостей, работает офлайн |
| Vitest + Playwright | Мини-раннер тестов в браузере (`tests/index.html`) | Без Node. Ключевые сценарии Playwright проверены вручную в браузере и частично покрыты тестами сервисов |
| SQL-миграции, RLS | Таблицы в одном JSON (`js/data/db.js`) с теми же именами и полями | Перенос в Postgres один к одному |
| «Ночь на понедельник» для адаптации | Правила адаптации прогоняются при каждой отметке и при открытии приложения / смене профиля | Фоновых задач нет; результат тот же, ключи не дают сработать дважды |

## Расчёты

- **Дата рождения Даши** — в ТЗ только «28 лет»; поставлено 01.01.1998, меняется в «Личных данных».
- **Коэффициент активности:** при наличии плана — по числу тренировок (1,375 при 1–3, 1,55 при 4 и больше); без плана — `activity_level` из профиля, если указан, иначе 1,2.
- **Дефицит для снижения веса:** нужный темп до дедлайна (без дедлайна — 0,75% веса в неделю) ограничивается 0,5–1% веса в неделю, затем дефицит ограничивается 15–20% расхода; 7700 ккал на кг.
- **Нижняя граница** применяется с округлением вверх до 50, остальное округляется до ближайших 50.
- **Углеводы ≥ 4 г/кг для забега:** если остатка калорий не хватает, жиры уменьшаются, но не ниже 0,6 г/кг; итоговая сумма макронутриентов может чуть превысить норму.
- **Силовая цель:** «+5–10%» → +5%, белок 1,8 г/кг.
- **Объём тела (measurement):** дефицит как у снижения веса с темпом по умолчанию.
- **Забег при второстепенной цели по весу:** норма берётся по второстепенной цели, углеводы — не ниже 4 г/кг.
- **Ручная норма:** по умолчанию действует с понедельника, есть галочка «применить к текущей неделе». Пока последняя норма ручная (или из Excel), автопересчёт показывается только подсказкой.
- **Первая автонорма** действует с текущего понедельника (иначе на текущую неделю не было бы бюджета); все последующие — с ближайшего понедельника.
- **Неделя ✓ без плана:** нужно не меньше 3 тренировок, как было в таблице Глеба.
- **«Можно в день»** = остаток / число незаполненных дней недели, включая прошедшие незаполненные.
- **Цвет дня:** между −30% и −5% от нормы — «хорошо» (зелёный).

## Цели

- Общий процент: если у части целей прогресс неизвестен, сумма нормируется по известным.
- Если сумма весов второстепенных больше 0,5, веса пропорционально уменьшаются до 0,5.
- Забег: «доля выполненных тренировок» — выполненные плановые от начала плана до вчера (сегодняшние — если уже отмечены). Внеплановые не входят.
- Регулярность: текущая неделя учитывается, как только норма набрана.
- Темп считается только для целей с дедлайном.

## Генератор плана

- Фазы округляются от общего числа недель: адаптация 20%, база 35%, развитие 28%, подводка для забега 10% (2–3 недели), специфика — остаток. Для целей без подводки доли масштабируются на 90%.
- Адаптация полной длины — после перерыва больше 4 недель или если непрерывный бег «не знаю»; иначе ~10% срока.
- Разгрузка — каждая 4-я неделя в фазах адаптации, базы и развития.
- Длинный бег: +5 мин/нед до 85, затем шаг = 10% недельного бегового времени, округлённый вниз до 5 (от 5 до 10 мин). Это даёт ровно эталон: 90, 95, 100, затем 110, 120, 130, 140, 150.
- Пик для забега = ожидаемое время × 0,7, округление до 10, в пределах 90–180 мин. Ожидаемое время = верхняя граница дистанции × трейловый темп + 10 мин на 100 м набора; набор неизвестен → 30 м/км (для дороги — 0).
- Подводка: 75% / 50% / 20% пика с округлением вниз до 5.
- Лесенка бег-ходьбы открывается по длительности длинного бега: 3/1 с 40 мин, 5/1 с 45, 8/2 с 50, 10/1 с 55, 15/1 с 60, 20/1 с 70, непрерывный с 75 (совпадает с эталоном). Ступень не снижается в разгрузку.
- «Горный» забег: трейл с неизвестным или ненулевым набором либо набор ≥ 300 м. Блоки наклона — в развитии и специфике, если рельефа нет, а дорожка с наклоном есть.
- Неделя старта: короткая пробежка за 3 дня до старта, силовые ближе 4 дней до старта убираются.
- Шаблоны силовых собираются по паттернам с весами тегов (основной тег +4, второй +2, «нравится» +1, «не нравится» исключает). Ходьба на дорожке в силовой Б — с базы (с 7-й недели, как в эталоне), в развитии подъём на платформу заменяется медленным спуском.
- Веса в плане — стартовые из анкеты; подсказка на карточке прибавляет 2,5 кг (штанга, блок) или 1 кг (гантели) за каждую прошлую такую же тренировку с самочувствием ≥ 6. Подробный журнал подходов — вне рамок версии.

## Адаптация

- «Самочувствие ≤ 4 два раза подряд» — по двум последним отметкам с самочувствием, если последняя не старше 7 дней.
- «< 80% плана» → план пересобирается со следующего понедельника от уровня текущей недели (неделя повторяется). Если из-за этого пик стал ниже, в причине пишется «пик срезан».
- Перерыв 7–13 дней → откат на 1 неделю, 14–20 → на 2, 21+ → на 3, с проверкой реалистичности (предупреждения генератора).
- Отмена пересборки возвращает предыдущую версию плана; отмена облегчения/роста/разгрузки снимает поправку с тренировок недели.
- Пересборка с текущей недели: прошедшие дни этой недели остаются за старым планом вместе с отметками.

## Рекомендации

- Скрытая рекомендация не возвращается в тот же период (ключ правила содержит день или неделю).
- Приоритеты: усталость, вчерашние калории, перебор, питание на длинном беге, взвешивание, недоедание, белок, отставание, плато, срок задачи, разгрузка, зимний бег.

## Импорт

- Базовый бюджет недели: константа в H или первое число 5000–50000 в формуле; если не найдено — бюджет предыдущей недели. Расхождения бюджета приложения и таблицы показываются в отчёте.
- Строка активности ищется по метке «Поход в зал» в строках r+2…r+6 (обычно r+4).
- Год взвешиваний — 2026, как в ТЗ.
- Записи помечаются `source = 'xlsx'`, повторный импорт обновляет их по (профиль, дата).
- Цели Глеба уже есть в начальных данных; импорт их не дублирует и обновляет только статус чек-апа (A311).

## Интерфейс

- «Динамика» встроена в главный экран отдельным разделом под блоками «сегодня / неделя / цель» (решение заказчика: экраны близки по смыслу). Старый адрес `#/dynamics` ведёт к этому разделу. Освободившееся место в нижней навигации занял раздел «Тело».
- Фото тела: таблица `body_photos` (дата, ракурс, заметка) и отдельное хранилище IndexedDB с Blob — полный снимок (JPEG, до 1600 px) и миниатюра (до 360 px). Фото привязаны к дате, а не к конкретному замеру: замеры для сравнения берутся последние не позже даты снимка. Удаление фото — только явное, с подтверждением.
- Сравнение фото: пара по умолчанию — самое раннее и самое позднее фото одного ракурса; пресеты «месяц / 3 месяца / год назад» берут ближайший к этой дате снимок. Режимы «Рядом» и «Шторка» (шторку можно тянуть по фото).

- Свайп листает недели в «Питании» и «Тренировках» и периоды в «Динамике».
- На компьютере нижняя навигация становится боковой, главный экран — в две колонки (слева 1–3 и 6, справа 4–5).
- Push-уведомлений нет (открытый вопрос ТЗ): напоминания только на главном экране.

## Дизайн

- Стиль по мотивам мерча Broke Boys, без логотипов и надписей: кислотно-жёлтый `#FFE704`, чёрный и белый; жёлтая шапка, чёрная нижняя навигация, чёрная плашка цели на главной, кнопки-таблетки, плоские светло-серые карточки.
- Фирменный шрифт референса (Druk Text Wide) платный, поэтому заголовки — бесплатный широкий Unbounded, текст — Golos Text (оба с кириллицей, Google Fonts). Шрифты кэшируются service worker'ом; при первом запуске без интернета используется системный шрифт.
- Жёлтый не используется для текста на белом (плохой контраст): в светлой теме акцентные тексты, линии графиков и кольцо прогресса — чёрные, жёлтый — заливка; в тёмной теме — наоборот.

## Версия 2: настройка, цели, безопасность

- **Порядок:** анкета подготовки → цели → расписание → приложение. Профиль создаётся автоматически при первом запуске. Выбор профиля при запуске появляется только когда профилей больше одного. PIN по умолчанию выключен и включается в настройках.
- **Сброс демо-данных:** при переходе на версию 2 прежние данные (демо Глеба и Даши) убираются, но их копия остаётся в браузере (Настройки → «Скачать прежние демо-данные»). Демо-профили в новом формате загружаются кнопкой «Добавить демо-профили».
- **Основная и дополнительные цели:** у целей больше нет веса в общем проценте (это было требование Google-таблицы). Общий процент — прогресс основной цели. Основных типов пять (снижение веса, набор, рост силы, забег, общая форма), дополнительных шесть (добавляются объём тела и «пробежать дистанцию», тип «задача/чек-ап» убран, так как не влиял на план).
- **Совместимость:** дополнительная цель допускается, только если она влияет на сценарий основной (таблица `COMPAT` в `js/domain/goals/scenario.js`); несвязанные и противоречащие цели добавить нельзя, объяснение показывается. Дубли основной (промежуточный рубеж) разрешены. При смене основной цели несочетаемые дополнительные уходят в архив.
- **Влияние дополнительных целей:** силовая цель ограничивает дефицит (15%, при забеге и силовой основной — 10%), поднимает белок до 1,8 г/кг и ставит упражнение первым в каждую силовую; «регулярность» задаёт минимум тренировок в неделю; «пробежать дистанцию» добавляет бег в план.
- **Оценка подготовки:** уровень (0–4) выносливости и силы считается по фактам: бег без остановки, ходьба, лестница, перерыв, отжимания, приседания, планка, рабочие веса, опыт. Перерыв больше 8 недель снижает оценку на 0,5, больше полугода — на 1. Вес приседа относительно веса тела усредняется с тестами. Общий уровень — округлённое среднее.
- **Здоровье:** медицинских вопросов и рекомендаций врача нет (приложение личное). Один флажок «бег и прыжки лучше исключить» и ИМТ от 35 → вместо бега ходьба с наклоном и велотренажёр; недовес (ИМТ < 18,5) → снижение веса недоступно.
- **Прохождение тренировки:** «Начать» доступно сегодня и вчера (если нет отметки). Галочки и ощущения по упражнениям → вес следующей тренировки по правилам `domain/progress.js`; две тяжёлые/лёгкие подряд дополнительно двигают план через `adapt`. Черновик хода тренировки хранится в localStorage устройства.
- **Проверки целей:** темп снижения веса > 1% в неделю — предупреждение, > 1,5% — опасно (нужна галочка подтверждения); ИМТ на финише < 18,5 — цель нельзя поставить; для забега минимум недель считается по формуле «базовые недели уровня × (км / 5)^0,75»; для силовой — максимальная недельная прибавка по уровню и отношение цели к весу тела. Серьёзные предупреждения не блокируют, кроме явно опасных (недовес, направление цели).
- **Тело:** вес вводится на главной, всё остальное (объёмы, история, фото, сравнение) — в Профиль → Тело и фото. Отдельной вкладки больше нет.
- **Первый план** строится с текущей недели (а не с даты старта цели): прошлое не планируется задним числом.

## Версия 3: облако и выпуск

- **Supabase как база, но «локально в первую очередь».** Все экраны по-прежнему работают с локальной базой в браузере, а модуль `js/sync` в фоне обменивается с облаком. Это даёт офлайн-режим и мгновенный отклик, а облако — общие данные на всех устройствах. Переписывать приложение под запросы к серверу не пришлось.
- **Одна универсальная таблица `records`** (`user_id, tbl, id, data jsonb, deleted, updated_at`) вместо отдельной таблицы под каждую сущность: структура локальных данных может меняться без миграций в Supabase. Ценой становится невозможность запросов по полям на стороне базы, но приложению они не нужны. При росте проекта таблицы можно разнести миграцией.
- **Защита данных:** вход по почте и паролю (Supabase Auth) и построчные правила доступа (RLS): пользователь видит только свои записи и свои фото. Публичный ключ anon лежит в коде открыто, это штатно; ключ service_role в приложении не используется. Вместо общего PIN-кода из первоначального ТЗ (он нужен был для сервера на Next.js) используются аккаунты.
- **Как находятся изменения:** сравнением хэшей строк с отправленными ранее, а не отслеживанием каждой записи в коде: надёжнее при любом способе изменения данных. Порядок ключей не влияет (jsonb меняет его).
- **Удаления** передаются «надгробиями». Записи с естественным ключом (еда и замеры за день) получают id из ключа, поэтому один день с двух устройств сливается в одну запись.
- **Конфликты:** побеждает устройство, синхронизировавшееся последним (push, затем pull). Для одного человека на 2–3 устройствах достаточно; для совместного редактирования одной записи нужно было бы время правки на каждую строку.
- **Не синхронизируется:** библиотека упражнений (одинакова у всех), настройки устройства (PIN, ключ ИИ, тема) и сам вход. Ключ ИИ из соображений безопасности остаётся только на устройстве.
- **Фото** лежат в закрытом бакете `photos` в папке с id пользователя; на другом устройстве скачиваются по требованию и кэшируются.
- **Тестовые версии не трогают реальные данные:** синхронизация включается только на адресах из `hosts` (`js/config.js`), localhost и любые другие копии работают в локальном режиме.
- **Выпуск: GitHub Pages, а не Vercel, из личного репозитория.** Репозиторий организации не подошёл: включать Pages там может только админ организации, а связаться с ним нельзя; личный публичный репозиторий даёт бесплатные Pages и полный доступ к настройкам. Workflow `pages.yml` после зелёных тестов выкладывает только нужные файлы приложения (без тестов, документации, схемы базы). Сборки нет, версия — в `js/version.js` и в имени кэша service worker. Минус по сравнению с Vercel: нет превью-ссылки на каждый пул-реквест.
- **Публичность сайта.** Pages открыт всем по ссылке даже у приватного репозитория, поэтому в публикуемых файлах нет личных данных (демо-профили вымышленные: Макс и Анна), а после регистрации пользователей нужно отключить регистрацию новых аккаунтов в Supabase.
- **Демо-профили** (`demo-max`, `demo-anna`) в коде вымышленные; прежние имена и данные остались только в приватной документации.
- **Автотесты** запускаются в GitHub Actions безголовым Chrome на каждый пул-реквест, раз в три дня пингуется Supabase, чтобы бесплатный проект не засыпал.
